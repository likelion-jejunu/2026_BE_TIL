- Spring Data JPA를 활용해서 지금까지 메모리를 활용해서 데이터를 저장하던 것을 넘어서서 DB에 저장하는 것을 배웠다. 또한 Entity 간의 관계를 설정해서 카테고리별로 상품을 묶어서 조회해 보았다.

### 2. 핵심 정리(내 언어로)
- JPA Repository는 인터페이스만 있으면 끝이다.
전에는 직접 리스트나 맵을 통해 데이터를 저장했지만 JPA를 사용하면 그러지 않아도 된다. JpaRepository를 상속받는 인터페이스 하나만 만들면 Spring이 알아서 구현체를 만들어주기 때문에 기본 CRUD 메서드를 사용할 수 있다.

- DTO를 사용해야 하는 이유
는 Item이 Category를 참조하고 Category가 Item 리스트를 다시 참조하는 양방향 구조라서 직렬화하면 무한루프가 발생하기 때문에, 들어올 때는 Request DTO, 나갈 때는 Response DTO로 변환해서 반환해야 한다.

- 연관관계 맵핑
오늘 내용 중 헷갈렸던 부분임. @ManyToOne과 @OneToMany를 같이 사용할 때 연관관계의 주인이 어느 쪽인지 이해해야 함
; 주인(@ManyToOne): FK(category_id)를 들고있는 쪽이고 여기서 수정해야 DB에 반영됨
; 거울(@OneToMany): FK는 없고 조회만 가능함

### 3. 실습 결과물
Category와 Item 엔티티를 연관관계로 연결해서 Postman으로 테스트까지 완료했다.

1. 카테고리 생성 
POST /categories
{ "name": "커피" }

→ { "id": 1, "name": "커피", "itemNames": [] }

2. 상품 생성과 카테고리 연결
POST /items
{ "name": "아메리카노", "price": 4500, "categoryId": 1 }

→ { "id": 1, "name": "아메리카노", "price": 4500, "categoryName": "커피" }

3. 카테고리로 묶어 조회
GET /categories/1

→ { "id": 1, "name": "커피", "itemNames": ["아메리카노"] }

### 4. 느낀 점
과제를 진행하면서 패키지명 언더바 개수 하나 차이로 Repository를 못찾는 에러가 났을 때, 코드 하나 차이로 결과물이 진행이 안된다는 말을 실감했다. 콘솔 로그를 꼼꼼히 읽는 습관을 좀 기를 필요를 느꼈던 순간이었다. 
그리고 1학기 7번의 세션을 진행하면서 Spring이 다 한다고 생각이 들면서도 동시에 그럴 수록 초반에 자바를 배우던 것의 중요성이 다시 한번 느껴졌다. 다시 한 번 복습을 해야겠다는 생각이 들었다.
개인적으로 4월부터 시작해서 만으로 3개월 정도의 시간을 채우면서 짧은 시간 안에 많은 것을 배워서 상당한 발전을 스스로 한 것 같다는 생각이 들어 뿌듯함이 듦과 동시에 많은 것을 배워 정리가 명확히 안되는 것을 체감한다. 그래서 복습의 필요성을 느끼는 것도 맞고 앞으로의 해커톤에서 내가 팀에 짐이 되지 않기 위해서는 더 분발해야 되겠다는 생각이 든다.
